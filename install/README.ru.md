# Team AI Box инструменты автономного пакета

Исходный установщик имеет лицензию MIT. Пакеты включают корневую лицензию, сторонний инвентарь и тексты лицензий в своем хэш-инвентаре. Это не приводит к повторному лицензированию моделей, служб Google, драйверов или зависимостей контейнеров как MIT. Прочтите [границы выпуска](../docs/open-source/RELEASING.ru.md) перед распространением; существующий полный тестовый пакет не имеет автоматического разрешения на распространение.

Клиенты запускают **`sudo ./install.sh` внутри подготовленного пакета**. Специалисты по сопровождению собирают этот пакет с помощью `build-package.sh`. Автономным клиентам не нужны Git, Node, Go, pip или общедоступные репозитории пакетов.

Для автоматической загрузки, сборки и установки из общедоступного клона запустите `sudo bash install/from-source.sh`. Сети в Китае могут использовать `--region cn`. См. [SOURCE-INSTALL.md](SOURCE-INSTALL.ru.md) для работы, возобновления и автономной передачи. Резюме поддерживается; только окончательный результат готовности устанавливает завершение установки. Успешной предварительной проверки или загрузки недостаточно.

Целью является новый DGX Spark с заводской системой Ubuntu 24.04 ARM64 и работающим Docker Engine, Compose v2, NVIDIA Container Toolkit/GPU и KVM. Программа установки не заменяет Docker/NVIDIA, не перезапускает Docker и не копирует учетные записи, базу данных, ключи или виртуальные машины устройства разработки.

> Записи о приемке частных установок остаются в хранилище исторических разработок. Они не являются ни файлами с общедоступным исходным кодом, ни входными данными для сборки. Существующие доказательства первой установки, возобновления и восстановления загрузки не перезапускаются только для публикации исходного кода и не квалифицируют произвольные вновь созданные образы или не предоставляют права на перераспределение сторонних двоичных файлов.

## Сопровождающие: подготовьте исходные данные для релиза

**Для новой общедоступной сборки GitHub начните с [PUBLIC-BUILD.md](PUBLIC-BUILD.ru.md).** Она охватывает общедоступные изображения, время работы камеры, загрузку/квантование моделей и встроенное ПО, не требуя изображений с устройства разработки. Приведенные ниже помощники по многоуровневым изображениям поддерживают инкрементные обновления проверенных артефактов; они не являются обязательными условиями для новой сборки.

Подготовка может использовать Интернет. Установка из поставляемого пакета не должна загружать зависимости. Узелу упаковки требуется Python 3.10+, PyYAML, Git, Docker, `dpkg-deb` и достаточно места. Модели и изображения могут быть большими; упаковщик сохраняет как извлеченное дерево, так и `.tar`, оценивая пространство на основе фактических входных данных. Он не сканирует все устройство разработки и не экспортирует доступные для записи слои из работающих контейнеров.

1. Подготовьте образы ARM64 из **одной версии** для всех необходимых ролей. Используйте точки входа сборки в `deploy/images/`, `deploy/appliance/` и соответствующие каталоги гостя/модели. API платформы, агент узла, планировщик и контроллер агента должны поддерживать локальные идентификаторы изображений; образ PostgreSQL должен содержать текущий манифест миграции, включая миграцию 116. Упаковщик не компилирует произвольный старый образ в текущий. При использовании проверенных родительских образов той же версии используйте `build_runtime_images.py --bases … --node-agent-binary … --output …` для создания пяти последующих образов. `--bases` — это сопоставление роли JSON с полным идентификатором изображения. Сначала создайте агент узла с помощью `GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build`. Этот помощник запрещает извлечение/сборку сети, запись идентификаторов родителя/источника и создание новых образов без развертывания или изменения живых тегов. Чистым ПЗУ Android также требуется текущий адаптер сети управления. Используйте `build_phone_images.py --bases <phone-role-image-ids.json> --output <new-directory>`, чтобы добавить `phone_network.py` в оба последующих слоя ПЗУ без доступа к сети или изменения данных ПЗУ. Он записывает точные идентификаторы изображений и дайджесты источников. Привяжите коляску Android к обоим новым идентификаторам, а не к предыдущим. Создайте Интернет и девять официальных приложений, используя `build_application_images.py --node-base <clean-arm64-node-image-id> --guacamole-image <offline-guacamole-image-id> --output <new-directory>`. Сначала создайте сеть, как указано в `apps/web/package.json`. Помощник использует рабочие файлы Dockerfile, исправляет веб-каталог `/opt/teamaibox/web` и сравнивает файлы изображений с текущими входными хэшами сборки. Не думайте, что образ контейнера разработки представляет собой полную веб-сборку: он может зависеть от дополнительных переменных статического каталога или содержать старый каталог. Этот автономный помощник не развертывается. Поместите все десять новых идентификаторов изображений во входные данные выпуска.
2. Соберите полные, чистые каталоги для шести моделей: конфигурации, шарды, токенизаторы, необходимый код и лицензии. Также подготовьте два чистых образа Android, UEFI `CODE.fd`/`VARS.fd`, `virtio.iso` и сценарии выполнения рисования. Не собирайте каталоги экземпляров телефонов, пользовательские диски, состояние входа в Google, ISO-образы пользователей или глобальные учетные данные. ПЗУ Android уже находятся внутри `phone-runtime` / `phone-google-runtime`; не копируйте второй диск. Каталоги активов `android-standard` / `android-google` содержат только происхождение, лицензии и `manifest.json`: `schemaVersion: 1`, `androidVersion: "17"`, `baseBuildId: "16102939"`, `systemFamily: "standard"` or `"google-play"` и `runtimeImageId: "sha256:…"`. Идентификатор должен соответствовать экспортированному образу среды выполнения. Каталог драйверов содержит только `virtio.iso`; каталог разработки, также содержащий `windows.iso`, отклонен.
3. Соберите два связанных хост-инструмента Linux ARM64, не устанавливая их на хост сборки:

   ```sh
   python3 install/build_guest_tools.py --output /build/artifacts/guest-host-tools
   ```

4. На подключенном к Интернету хосте сборки ARM64 соберите зависимости хост-инструмента, используя явный локальный образ Ubuntu 24.04. Используйте идентификатор образа, проверенный на этом хосте, а не идентификатор, скопированный с устройства разработки:

   ```sh
   python3 install/collect_host_packages.py \
     --base-image "$UBUNTU_ARM64_IMAGE_ID" --output /build/artifacts/host-packages
   ```

   Собирайте только зависимости для cryptsetup, ext4, USB/камер, инструментов создания образов QEMU, сетевых и небольших системных утилит. Docker,Containerd, NVIDIA, CUDA и пакеты замены ядра запрещены. При установке предоставляются только недостающие инструменты; apt считывает локальный файловый репозиторий пакета с помощью `--no-download --no-remove` без резервного онлайн-восстановления.

5. Создайте манифест ввода-выпуска и укажите **явные пути к артефактам и идентификаторы содержимого локальных изображений**:

   ```sh
   python3 install/prepare-release.py --template /build/artifact-inputs.json
   python3 install/prepare-release.py --inputs /build/artifact-inputs.json \
     --output /build/prepared-release
   ```

   Шаблон включает в себя все 41 роль изображения и 12 категорий внешних ресурсов; Инструменты создают еще один фабричный актив. Заполнители не могут войти в пакет. `sourceCommit` должен соответствовать оформлению заказа, `agentVersion` фактической сборке агента и `hostPackageCollection` шагу 4 `collection.json`. Пути к хосту сборки — это входные данные коллекции, а не конфигурация среды выполнения клиента. Используйте текущий заводской генератор: маршруты `drawing.automatic` / `drawing.fast` пользовательского интерфейса чертежа должны соответствовать конфигурации локальной модели. Здоровье работника или прямой звонок модели сами по себе не определяют готовность приложения. Упаковка отклоняет устаревшие заводские шаблоны, в которых отсутствуют эти сопоставления.

Контракт роли образа сообщается `python3 install/package.py --describe-contract`:

- Ядро, Интернет, групповой диск, обмен сообщениями, шлюзы, планировщик, обслуживание, плагины, изолированные программные среды динамических агентов и шлюзы источников пакетов.
- Девять плагинов приложений, шесть рабочих моделей офиса и среда выполнения ASR/динамика по требованию.
- Стандартный Android, Google Android, компьютерная среда выполнения и веб-шлюзы/аудиошлюзы.
- Кастинг-приемник, медиаобработка и СФУ.

Две роли могут использовать один идентификатор контента изображения; его архив экспортируется только один раз. Индексы шардов модели также проверяются: совпадение хэшей файлов не оправдывает отсутствие шарда. Инструменты хоста должны быть настоящими двоичными файлами ARM64 ELF.

## Сборка пакета

```sh
./install/build-package.sh --release /build/prepared-release/release-input.json \
  --output /build/output
```

Выходные данные: `teamaibox-<releaseId>-linux-arm64.tar`, его файл `.sha256` и извлеченный каталог. Копирование, экспорт изображений, хеширование и архивирование происходят во временном каталоге до публикации окончательной контрольной суммы. Существующие выходные данные не перезаписываются; прерванная сборка не должна выглядеть как полноценный релиз. Для изменений только для установщика с неизмененными идентификаторами изображений используйте `--image-cache <previous-extracted-package>`. Весь старый пакет проверяется перед повторным использованием его архивов по фактическому идентификатору образа, а новый пакет проверяется еще раз. Никакие данные не берутся из старой установки или слоя, доступного для записи в контейнере. Это позволяет избежать повторного экспорта сотен ГБ идентичных изображений.

Обычный выпуск требует, чтобы исходные файлы в комплекте принадлежали объявленному коммиту Git. Явный `--allow-working-tree` создает кандидата на разработку; его манифест записывает `candidate: true` и измененные файлы. Прохождение целенаправленного принятия не превращает несвязанный исходный код в опубликованный выпуск.

Компоновка упаковки:

```text
teamaibox-<releaseId>-linux-arm64/
  install.sh, installer.py, offline_common.py, offline_host_packages.py
  README.zh-CN.md, release.json, checksums.sha256
  images/          # Docker archives deduplicated by content ID
  assets/          # Models, Android, computers, tools and factory configuration by role
  host-packages/   # Complete .deb dependency set
  runtime/         # Installer adapters and recovery-tool module closure
```

Проверьте независимо с помощью `./install/build-package.sh --verify /build/output/teamaibox-<releaseId>-linux-arm64`. Это проверяет целостность; это не доказывает успешную загрузку нового оборудования.

## Клиенты: офлайн-установка и возобновление работы

Прочтите [руководство по установке пакета](PACKAGE-README.ru.md). Корень по умолчанию — `/srv/teamaibox/installation`. LUKS/ext4 создается только внутри нового `volume/data.img`, а не на системном диске или существующих дисках. Пул данных использует доступное хранилище за вычетом физического запаса безопасности, а не фиксированного ограничения в 256 ГиБ. Модели, бизнес-файлы и гостевые данные находятся в зашифрованном томе; существующий Docker управляет образами контейнеров.

При новой установке создается администратор `admin` с начальным паролем `admin`. Обычных пользователей создает администратор. Измените первоначальный пароль перед доставкой/использованием. Это применимо только к пустой базе данных учетных записей: возобновление, повторный запуск, перезагрузка и обновление не сбрасывают существующие учетные записи или пароли. Идентификаторы устройств, учетные данные служб, сертификаты и коды восстановления администратора генерируются независимо, а не копируются с другого устройства. Первоначальная подготовка кэша ядра графического процессора выполняется на устройстве с использованием встроенных инструментов и моделей; совместимые кэши сохраняются. Восстановление загрузки сначала восстанавливает данные и службы устройств, затем основные службы и отдельных работников ИИ. Программа установки запускается только во время установки; он не добавляет резидентного менеджера установщика.

После прерывания повторите исходную команду. Выполненные шаги проверяются; не скрывайте конфликты, удаляя данные или воссоздавая контейнеры. Повторный запуск завершенной установки той же версии только проверяет ее; разные версии используют формальный путь обновления. Подробности об ошибках находятся в `install-state.json`, `readiness.json` и записях этапов в корне установки.

## Границы проверки

Тесты, специфичные для установщика, используют небольшие структурные артефакты, временные файлы и изолированные автономные базы данных/демоны Docker. Им не разрешается обращаться к бизнес-базам данных или монтировать существующие диски виртуальных машин. Для настоящей новой установки требуется совместимый DGX Spark, явно предназначенный для этой цели; не стирайте данные с бизнес-устройства. Приемка охватывает минимальный запуск, возобновление и восстановление загрузки для новой установки, а не несвязанные бизнес-тесты. Сама по себе подготовка к выпуску исходного кода не удаляет, не переустанавливает и не развертывает существующие устройства.

На хосте сборки запустите `sudo python3 install/verify_bundle_offline.py --package <extracted-package> --output <new-test-directory>`, чтобы импортировать полный пакет в отдельный демон Docker с пустым кешем и без общедоступной сети. Он не вызывает сценарий новой установки, не использует графический процессор, не монтирует каталоги клиентов и не перезагружает систему Docker. В его отчете явно не говорится о полной установке оборудования. Тестовые изображения остаются в выделенном тестовом каталоге, требуют дополнительного дискового пространства и не попадают в хранилище образов системы Docker.
