# Team AI Box เครื่องมือแพ็คเกจออฟไลน์

โปรแกรมติดตั้งดั้งเดิมได้รับใบอนุญาต MIT แพ็คเกจประกอบด้วยสิทธิ์ใช้งานรูท พื้นที่โฆษณาของบุคคลที่สาม และข้อความสิทธิ์การใช้งานในคลังแฮชไฟล์ การดำเนินการนี้ไม่อนุญาตรุ่นโมเดล บริการของ Google ไดรเวอร์ หรือการอ้างอิงคอนเทนเนอร์เป็น MIT อ่าน [ขอบเขตการเผยแพร่](../docs/open-source/RELEASING.th.md) ก่อนเผยแพร่ แพคเกจการทดสอบที่สมบูรณ์ที่มีอยู่ไม่มีการกวาดล้างการแจกจ่ายซ้ำโดยอัตโนมัติ

ลูกค้าเรียกใช้ **`sudo ./install.sh` ภายในแพ็คเกจที่เตรียมไว้** ผู้ดูแลสร้างแพ็คเกจนั้นด้วย `build-package.sh` ลูกค้าออฟไลน์ไม่จำเป็นต้องมี Git, Node, Go, pip หรือที่เก็บแพ็คเกจสาธารณะ

สำหรับการดาวน์โหลด สร้าง และติดตั้งโดยอัตโนมัติจากโคลนสาธารณะ ให้รัน `sudo bash install/from-source.sh` เครือข่ายในประเทศจีนสามารถใช้ `--region cn` ได้ ดู [SOURCE-INSTALL.md](SOURCE-INSTALL.th.md) สำหรับการดำเนินการ การดำเนินการต่อ และการโอนแบบออฟไลน์ รองรับเรซูเม่; เฉพาะผลความพร้อมขั้นสุดท้ายเท่านั้นที่จะกำหนดความสมบูรณ์ในการติดตั้ง การ preflight หรือการดาวน์โหลดที่ประสบความสำเร็จนั้นไม่เพียงพอ

เป้าหมายคือ DGX Spark ใหม่ที่มีระบบ Ubuntu 24.04 ARM64 จากโรงงานและ Docker Engine ที่ใช้งานได้, Compose v2, NVIDIA Container Toolkit/GPU และ KVM โปรแกรมติดตั้งจะไม่แทนที่ Docker/NVIDIA รีสตาร์ท Docker หรือคัดลอกบัญชี ฐานข้อมูล คีย์ หรือเครื่องเสมือนของอุปกรณ์สำหรับการพัฒนา

> บันทึกการยอมรับการติดตั้งส่วนตัวจะยังคงอยู่ในพื้นที่เก็บข้อมูลการพัฒนาในอดีต ไม่ใช่ไฟล์ต้นฉบับสาธารณะหรืออินพุตบิวด์ หลักฐานการติดตั้งครั้งแรก ประวัติย่อ และการกู้คืนการบูตที่มีอยู่จะไม่ถูกเรียกใช้ซ้ำสำหรับการเผยแพร่แหล่งที่มาเท่านั้น และไม่เข้าข่ายอิมเมจที่สร้างขึ้นใหม่ตามอำเภอใจ หรือให้สิทธิ์ในการแจกจ่ายซ้ำสำหรับไบนารีของบุคคลที่สาม

## ผู้ดูแล: เตรียมอินพุตการปล่อย

**สำหรับ GitHub สาธารณะเวอร์ชันใหม่ ให้เริ่มต้นด้วย [PUBLIC-BUILD.md](PUBLIC-BUILD.th.md)** ซึ่งครอบคลุมรูปภาพสาธารณะ รันไทม์ของกล้อง การดาวน์โหลดโมเดล/การหาปริมาณ และเฟิร์มแวร์ โดยไม่ต้องใช้อิมเมจจากอุปกรณ์สำหรับการพัฒนา ตัวช่วยรูปภาพแบบเลเยอร์ด้านล่างรองรับการอัปเดตส่วนเพิ่มของอาร์ติแฟกต์ที่ได้รับการยืนยัน ไม่ใช่ข้อกำหนดเบื้องต้นสำหรับบิลด์ใหม่

การเตรียมตัวอาจใช้อินเตอร์เน็ต การติดตั้งจากแพ็คเกจที่จัดส่งจะต้องไม่ดาวน์โหลดการขึ้นต่อกัน โฮสต์บรรจุภัณฑ์ต้องการ Python 3.10+, PyYAML, Git, Docker, `dpkg-deb` และพื้นที่เก็บข้อมูลที่เพียงพอ โมเดลและรูปภาพอาจมีขนาดใหญ่ ผู้ทำแพ็กเกจจะเก็บทั้งแผนผังที่แยกออกมาและ `.tar` เพื่อประมาณพื้นที่จากอินพุตจริง ไม่สแกนอุปกรณ์การพัฒนาทั้งหมดหรือส่งออกเลเยอร์ที่เขียนได้จากการรันคอนเทนเนอร์

1. เตรียมอิมเมจ ARM64 จาก **เวอร์ชันเผยแพร่หนึ่งเวอร์ชัน** สำหรับบทบาทที่จำเป็นทั้งหมด ใช้จุดเข้าบิลด์ภายใต้ `deploy/images/`, `deploy/appliance/` และไดเร็กทอรีผู้เยี่ยมชม/โมเดลที่เกี่ยวข้อง Platform API, Node Agent, scheduler และ agent controller ต้องรองรับ ID รูปภาพในเครื่อง อิมเมจ PostgreSQL ต้องมีรายการการโยกย้ายปัจจุบัน รวมถึงการย้าย 116 ด้วย ผู้ทำแพ็กเกจจะไม่รวบรวมอิมเมจเก่าที่กำหนดเองให้เป็นอิมเมจปัจจุบัน ด้วยอิมเมจพาเรนต์เวอร์ชันเดียวกันที่ได้รับการยืนยันแล้ว ให้ใช้ `build_runtime_images.py --bases … --node-agent-binary … --output …` เพื่อสร้างอิมเมจลำดับที่ 5 `--bases` คือแมป JSON-to-image-ID แบบเต็ม ขั้นแรกให้สร้าง Node Agent ด้วย `GOOS=linux GOARCH=arm64 CGO_ENABLED=0 go build` ตัวช่วยนี้ห้ามการดึง/การสร้างเครือข่าย บันทึกข้อมูลประจำตัวหลัก/แหล่งที่มา และสร้างรูปภาพใหม่โดยไม่ต้องปรับใช้หรือเปลี่ยนแปลงแท็กที่ทำงานอยู่ Clean Android ROM ยังต้องใช้อะแดปเตอร์เครือข่ายควบคุมปัจจุบันด้วย ใช้ `build_phone_images.py --bases <phone-role-image-ids.json> --output <new-directory>` เพื่อเพิ่ม `phone_network.py` ไปยังเลเยอร์ตัวต่อจาก ROM ทั้งสองโดยไม่มีการเข้าถึงเครือข่ายหรือการเปลี่ยนแปลงข้อมูล ROM โดยจะบันทึกรหัสรูปภาพและการสรุปแหล่งที่มาที่แน่นอน ผูกรถเทียมข้าง Android เข้ากับ ID ใหม่ทั้งสอง ID ไม่ใช่ ID ก่อนหน้า สร้างเว็บและแอปอย่างเป็นทางการเก้าแอปโดยใช้ `build_application_images.py --node-base <clean-arm64-node-image-id> --guacamole-image <offline-guacamole-image-id> --output <new-directory>` ขั้นแรกให้สร้างเว็บตามที่ระบุโดย `apps/web/package.json` ตัวช่วยใช้ Production Dockerfiles แก้ไขไดเร็กทอรีเว็บที่ `/opt/teamaibox/web` และเปรียบเทียบไฟล์รูปภาพกับแฮชอินพุตบิลด์ปัจจุบัน อย่าถือว่าอิมเมจคอนเทนเนอร์การพัฒนาเป็นเว็บบิลด์ที่สมบูรณ์ เนื่องจากอาจขึ้นอยู่กับตัวแปรสแตติกไดเร็กทอรีเพิ่มเติมหรือมีไดเร็กทอรีเก่า ตัวช่วยออฟไลน์นี้ไม่ได้ปรับใช้ ใส่ ID รูปภาพใหม่ทั้ง 10 รายการลงในอินพุตการเผยแพร่
2. รวบรวมไดเร็กทอรีที่สมบูรณ์และสะอาดสำหรับหกรุ่น: การกำหนดค่า ส่วนย่อย โทเค็น โค้ดที่จำเป็น และใบอนุญาต นอกจากนี้ ให้เตรียมอิมเมจ Android ที่ชัดเจนสองอิมเมจ UEFI `CODE.fd`/`VARS.fd`, `virtio.iso` และสคริปต์รันไทม์การวาด อย่ารวบรวมไดเร็กทอรีอินสแตนซ์โทรศัพท์, ดิสก์ผู้ใช้, สถานะการเข้าสู่ระบบ Google, ISO ของผู้ใช้ หรือข้อมูลรับรองส่วนกลาง ROM Android อยู่ภายใน `phone-runtime` / `phone-google-runtime` แล้ว; อย่าคัดลอกดิสก์แผ่นที่สอง ไดเร็กทอรีสินทรัพย์ `android-standard` / `android-google` มีเพียงแหล่งที่มา ใบอนุญาต และ `manifest.json`: `schemaVersion: 1`, `androidVersion: "17"`, `baseBuildId: "16102939"`, `systemFamily: "standard"` or `"google-play"` และ `runtimeImageId: "sha256:…"` รหัสต้องตรงกับอิมเมจรันไทม์ที่ส่งออก ไดเร็กทอรีไดรเวอร์มีเพียง `virtio.iso`; ไดเร็กทอรีการพัฒนาที่มี `windows.iso` ถูกปฏิเสธด้วย
3. สร้างเครื่องมือโฮสต์ Linux ARM64 ที่รวมมาสองชุดโดยไม่ต้องติดตั้งบนโฮสต์ build:

   ```sh
   python3 install/build_guest_tools.py --output /build/artifacts/guest-host-tools
   ```

4. บนโฮสต์บิลด์ ARM64 ที่เชื่อมต่ออินเทอร์เน็ต ให้รวบรวมการพึ่งพาเครื่องมือโฮสต์โดยใช้อิมเมจ Ubuntu 24.04 ในเครื่องที่ชัดเจน ใช้รหัสรูปภาพที่ยืนยันแล้วบนโฮสต์นั้น ไม่ใช่รหัสที่คัดลอกมาจากอุปกรณ์สำหรับการพัฒนา:

   ```sh
   python3 install/collect_host_packages.py \
     --base-image "$UBUNTU_ARM64_IMAGE_ID" --output /build/artifacts/host-packages
   ```

   รวบรวมเฉพาะการขึ้นต่อกันสำหรับการตั้งค่าการเข้ารหัส, ext4, USB/กล้อง, เครื่องมืออิมเมจ QEMU, ระบบเครือข่ายและยูทิลิตี้ระบบขนาดเล็ก ห้ามใช้ Docker, Containerd, NVIDIA, CUDA และแพ็คเกจการเปลี่ยนเคอร์เนล การติดตั้งจะจัดหาเครื่องมือที่ขาดหายไปเท่านั้น apt อ่านที่เก็บไฟล์ในเครื่องของแพ็คเกจด้วย `--no-download --no-remove` โดยไม่มีทางเลือกออนไลน์

5. สร้างรายการอินพุต release และจัดหา **เส้นทางอาร์ติแฟกต์ที่ชัดเจนและ ID เนื้อหารูปภาพในเครื่อง**:

   ```sh
   python3 install/prepare-release.py --template /build/artifact-inputs.json
   python3 install/prepare-release.py --inputs /build/artifact-inputs.json \
     --output /build/prepared-release
   ```

   เทมเพลตประกอบด้วยบทบาทรูปภาพทั้งหมด 41 บทบาทและหมวดหมู่เนื้อหาภายนอก 12 หมวดหมู่ ทรัพย์สินโรงงานอีกชิ้นหนึ่งถูกสร้างขึ้นโดยเครื่องมือ ตัวยึดตำแหน่งไม่สามารถเข้าสู่แพ็คเกจได้ `sourceCommit` ต้องตรงกับการชำระเงิน `agentVersion` บิลด์ Agent จริง และ `hostPackageCollection` ขั้นตอนที่ 4 `collection.json` เส้นทาง Build-host เป็นอินพุตการรวบรวม ไม่ใช่การกำหนดค่ารันไทม์ของลูกค้า ใช้ตัวสร้างโรงงานปัจจุบัน: เส้นทาง `drawing.automatic` / `drawing.fast` ของ UI การวาดจะต้องตรงกับการกำหนดค่าโมเดลในเครื่อง สุขภาพของผู้ปฏิบัติงานหรือการเรียกโมเดลโดยตรงเพียงอย่างเดียวไม่ได้สร้างความพร้อมของแอปพลิเคชัน บรรจุภัณฑ์ปฏิเสธเทมเพลตโรงงานเก่าที่ไม่มีการแมปเหล่านี้

สัญญาบทบาทรูปภาพรายงานโดย `python3 install/package.py --describe-contract`:

- แกนหลัก, เว็บ, ไดรฟ์ของทีม, การส่งข้อความ, เกตเวย์, ตัวกำหนดเวลา, การบำรุงรักษา, ปลั๊กอิน, แซนด์บ็อกซ์เอเจนต์ไดนามิก และเกตเวย์แหล่งที่มาของแพ็คเกจ
- ปลั๊กอินแอปพลิเคชันเก้ารายการ พนักงานโมเดลสำนักงานหกคน และรันไทม์ ASR/ลำโพงตามความต้องการ
- Android มาตรฐาน, Google Android, รันไทม์ของคอมพิวเตอร์ และเกตเวย์การแสดงผล/เสียงบนเว็บ
- เครื่องรับแบบหล่อ การประมวลผลสื่อ และ SFU

สองบทบาทอาจแชร์ ID เนื้อหารูปภาพเดียว ไฟล์เก็บถาวรจะถูกส่งออกเพียงครั้งเดียว มีการตรวจสอบดัชนีชิ้นส่วนโมเดลด้วย: แฮชของไฟล์ที่ตรงกันจะไม่แก้ตัวว่าชิ้นส่วนที่หายไป เครื่องมือโฮสต์ต้องเป็นไบนารี ARM64 ELF จริง

## สร้างแพ็คเกจ

```sh
./install/build-package.sh --release /build/prepared-release/release-input.json \
  --output /build/output
```

เอาต์พุตคือ `teamaibox-<releaseId>-linux-arm64.tar`, ไฟล์ `.sha256` และไดเร็กทอรีที่แยกออกมา การคัดลอก การส่งออกรูปภาพ การแฮช และการเก็บถาวรจะเกิดขึ้นในไดเร็กทอรีชั่วคราวก่อนที่จะเผยแพร่เช็คซัมขั้นสุดท้าย เอาต์พุตที่มีอยู่จะไม่ถูกเขียนทับ บิลด์ที่ถูกขัดจังหวะต้องไม่ดูเหมือนเป็นรีลีสที่สมบูรณ์ สำหรับการเปลี่ยนแปลงเฉพาะตัวติดตั้งซึ่งมีข้อมูลระบุตัวตนของรูปภาพที่ไม่เปลี่ยนแปลง ให้ใช้ `--image-cache <previous-extracted-package>` แพ็คเกจเก่าทั้งหมดได้รับการตรวจสอบก่อนที่ไฟล์เก็บถาวรจะถูกนำมาใช้ซ้ำด้วย ID รูปภาพจริง และแพ็คเกจใหม่จะได้รับการตรวจสอบอีกครั้ง ไม่มีการนำข้อมูลจากการติดตั้งเก่าหรือเลเยอร์ที่สามารถเขียนคอนเทนเนอร์ได้ วิธีนี้จะหลีกเลี่ยงการส่งออกภาพที่เหมือนกันหลายร้อย GB อีกครั้ง

การเปิดตัวแบบปกติต้องการให้ไฟล์ต้นฉบับที่รวมมานั้นเป็นของคอมมิต Git ที่ประกาศไว้ `--allow-working-tree` ที่ชัดเจนสร้างผู้สมัครเพื่อการพัฒนา รายการบันทึก `candidate: true` และไฟล์ที่เปลี่ยนแปลง การผ่านการยอมรับที่มุ่งเน้นไม่ได้เปลี่ยนแหล่งที่มาที่ไม่มีข้อผูกมัดให้กลายเป็นการเผยแพร่ที่เผยแพร่

ยืนยันอย่างอิสระด้วย `./install/build-package.sh --verify /build/output/teamaibox-<releaseId>-linux-arm64` นี่เป็นการตรวจสอบความสมบูรณ์ มันไม่ได้พิสูจน์ว่าสามารถบู๊ตฮาร์ดแวร์ใหม่ได้สำเร็จ

## ลูกค้า: การติดตั้งแบบออฟไลน์และดำเนินการต่อ

อ่าน [คู่มือการติดตั้งแพ็คเกจ](PACKAGE-README.th.md) รูทเริ่มต้นคือ `/srv/teamaibox/installation` LUKS/ext4 ถูกสร้างขึ้นภายใน `volume/data.img` ใหม่เท่านั้น ไม่ใช่บนดิสก์ระบบหรือดิสก์ที่มีอยู่ พูลข้อมูลใช้พื้นที่จัดเก็บข้อมูลที่มีอยู่ลบด้วยความปลอดภัยทางกายภาพ ไม่ใช่ขีดจำกัด 256 GiB คงที่ โมเดล ไฟล์ธุรกิจ และข้อมูลแขกอยู่ในวอลลุ่มที่เข้ารหัส Docker ที่มีอยู่จัดการอิมเมจคอนเทนเนอร์

การติดตั้งใหม่จะสร้างผู้ดูแลระบบ `admin` ด้วยรหัสผ่านเริ่มต้น `admin` ผู้ใช้ทั่วไปถูกสร้างขึ้นโดยผู้ดูแลระบบ เปลี่ยนรหัสผ่านเริ่มต้นก่อนส่งมอบ/ใช้งาน สิ่งนี้ใช้ได้กับฐานข้อมูลบัญชีที่ว่างเปล่าเท่านั้น: ดำเนินการต่อ รันใหม่ รีบูต และอัปเกรด จะไม่รีเซ็ตบัญชีหรือรหัสผ่านที่มีอยู่ ข้อมูลระบุตัวตนของอุปกรณ์ ข้อมูลรับรองการบริการ ใบรับรอง และรหัสกู้คืนของผู้ดูแลระบบจะถูกสร้างขึ้นอย่างอิสระ โดยไม่มีการคัดลอกจากอุปกรณ์อื่น การเตรียมแคชเคอร์เนล GPU เริ่มต้นทำงานบนอุปกรณ์โดยใช้เครื่องมือและโมเดลที่แถมมา แคชที่เข้ากันได้จะถูกเก็บไว้ การกู้คืนบูทจะกู้คืนข้อมูลและบริการอุปกรณ์ก่อน จากนั้นจึงกู้คืนบริการหลักและผู้ปฏิบัติงาน AI แต่ละคน โปรแกรมติดตั้งจะทำงานระหว่างการติดตั้งเท่านั้น มันเพิ่มไม่มีผู้จัดการการติดตั้งถิ่นที่อยู่

หลังจากหยุดชะงัก ให้ทำซ้ำคำสั่งเดิม ขั้นตอนที่เสร็จสมบูรณ์ได้รับการตรวจสอบแล้ว อย่าซ่อนข้อขัดแย้งด้วยการลบข้อมูลหรือสร้างคอนเทนเนอร์ใหม่ การเรียกใช้การติดตั้งเวอร์ชันเดียวกันที่เสร็จสมบูรณ์อีกครั้งจะเป็นการตรวจสอบเท่านั้น เวอร์ชันต่างๆ จะใช้เส้นทางการอัพเกรดอย่างเป็นทางการ รายละเอียดความล้มเหลวอยู่ใน `install-state.json`, `readiness.json` และบันทึกขั้นตอนภายใต้รูทการติดตั้ง

## ขอบเขตการตรวจสอบ

การทดสอบเฉพาะตัวติดตั้งใช้โครงสร้างขนาดเล็ก ไฟล์ชั่วคราว และฐานข้อมูลออฟไลน์/Docker daemons ที่แยกออกมา พวกเขาจะต้องไม่เข้าถึงฐานข้อมูลธุรกิจหรือเมานต์ดิสก์ VM ที่มีอยู่ การติดตั้งใหม่จริงต้องใช้ DGX Spark ที่เข้ากันได้ซึ่งกำหนดไว้อย่างชัดเจนเพื่อจุดประสงค์นั้น อย่าลบอุปกรณ์ทางธุรกิจ การยอมรับครอบคลุมการกู้คืนการเริ่มต้นระบบ การดำเนินการต่อ และการบูตขั้นต่ำสำหรับการติดตั้งใหม่ ไม่ใช่การทดสอบทางธุรกิจที่ไม่เกี่ยวข้อง การเตรียมการปล่อยซอร์สนั้นจะไม่ลบ ติดตั้งใหม่ หรือปรับใช้อุปกรณ์ที่มีอยู่

บนโฮสต์บิลด์ ให้รัน `sudo python3 install/verify_bundle_offline.py --package <extracted-package> --output <new-test-directory>` เพื่อนำเข้าแพ็กเกจแบบเต็มไปยัง Docker daemon ที่แยกต่างหากซึ่งมีแคชว่างและไม่มีเครือข่ายสาธารณะ ไม่เรียกใช้สคริปต์การติดตั้งใหม่ ใช้ GPU ติดตั้งไดเร็กทอรีของลูกค้า หรือรีสตาร์ทระบบ Docker รายงานไม่ได้อ้างสิทธิ์ในการติดตั้งฮาร์ดแวร์แบบเต็มอย่างชัดเจน อิมเมจทดสอบจะยังคงอยู่ในไดเร็กทอรีทดสอบเฉพาะ ต้องการพื้นที่ดิสก์เพิ่มเติม และไม่ต้องเข้าสู่ที่เก็บอิมเมจของ Docker ของระบบ
